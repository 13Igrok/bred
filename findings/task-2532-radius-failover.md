## 2. На какой отдел перевести

**Задачу нельзя перевести целиком на один отдел — она междисциплинарная.** Правильнее разбить на две подзадачи с разными владельцами.

### 2.1. Сетевой отдел (или сетевые инженеры) — блоки A и B
- Управление DHCP-лизой у абонентов — параметр живёт на BRAS/DHCP-сервере, не на RADIUS-сервере.
- Настройка автопереключения между двумя RADIUS — делается **в конфиге BRAS** (radius-server group / dead-time), а не на сервере.
- Задавать вопросы по BRAS, площадкам, текущим лизам — сюда.

**Почему именно сюда основная часть:** ключевая часть заявки (переключение) реализуется на BRAS. Это сетевое оборудование, оно **не описано в аудите вообще** — значит, текущий исполнитель не может закрыть задачу из тех данных, что есть.

### 2.2. Отдел эксплуатации ИТ / платформы BGBilling — блок C
- Разворачивание и настройка второго экземпляра `BGInetAccess`/`BGInetAccounting`.
- Обеспечение идентичности shared-secret на обоих RADIUS.
- Согласование, что второй экземпляр пишет accounting в ту же БД корректно.
- Лицензирование BGBilling на второй узел (см. §5, п.3).

| **ЮТК Ростов** | — | **в аудите отсутствует** | — | — |

> ⚠️ **ЮТК Ростов отдельным хостом в аудите нет.** grep по всем 79 отчётам: «Ростов» не встречается. Если под Ростовом свой BRAS и свой RADIUS — они не описаны, и построить схему по ним сейчас нельзя.

### 3.2. Как устроен RADIUS

На всех пяти узлах **одинаковая архитектура**:

- RADIUS — **не FreeRADIUS**, а Java-приложения BGBilling Inet: `BGInetAccess` (auth) + `BGInetAccounting` (accounting), запускаются **от root**.
- **Локальной СУБД на RADIUS-сервере НЕТ** (`ActiveMQ/nginx/СУБД НЕТ` — прямо в отчётах).
- Значит авторизация идёт по сети в БД: `RADIUS → ProxySQL:6033 → MySQL на bg-core`.
- Портов нет: web, ActiveMQ, СУБД.

```
Порт 1812/udp  RADIUS Authentication  0.0.0.0
Порт 1813/udp  RADIUS Accounting      0.0.0.0
Порт 2001/udp  BGInet (NAS/CoA)       0.0.0.0
Порт 1951/tcp  BGInet упр.-консоль    0.0.0.0  ← БЕЗ аутентификации
Порт 1952/tcp  BGInet сервис          0.0.0.0
```

### 3.3. Главный вывод из аудита для этой задачи

**Один RADIUS на домен.** Второго экземпляра нет. То есть сейчас нечего переключать — failover невозможен физически, пока не поднят второй сервер.

**И ещё одна вещь, которая важнее, чем кажется:** RADIUS без локальной БД. Поэтому резервирование самого RADIUS **бесполезно, если упал ProxySQL или MySQL на bg-core** — авторизация всё равно встанет. Схема переключения обязана покрывать всю цепочку, а не только RADIUS-хост.

## 4. Схема переключения

### 4.1. Как есть сейчас (одна точка отказа на домен)

```
                     абонент (PPPoE / IPoE)
                              │
                    ┌─────────▼─────────┐
                    │       BRAS        │   ← сетевой отдел
                    │  (Ростов / РТЦ /  │
                    │     ЮТК)          │
                    └─────────┬─────────┘
                              │ RADIUS 1812/1813
                              │ (один сервер, dead = всё упало)
                    ┌─────────▼─────────┐
                    │  bg-radius-<домен>│   ← отказ 1
                    │  BGInetAccess     │      (EOL Debian 11)
                    │  BGInetAccounting │
                    └─────────┬─────────┘
                              │ MySQL 3306 через ProxySQL 6033
                    ┌─────────▼─────────┐
                    │    ProxySQL       │   ← отказ 2
                    └─────────┬─────────┘
                              │
                    ┌─────────▼─────────┐
                    │ MySQL на bg-core  │   ← отказ 3
                    └───────────────────┘
```

Любой из трёх узлов падает → абоненты не авторизуются до восстановления.

### 4.2. Целевая схема

```
                       абонент
                          │
                ┌─────────▼─────────┐
                │       BRAS        │
                │  primary +        │  ← dead-time, dead-criteria,
                │  secondary radius │     сервер считается мёртвым
                └──┬────────────┬───┘
                   │            │
      ┌────────────▼──┐    ┌────▼────────────┐
      │ bg-radius-A   │    │ bg-radius-B     │   ← два экземпляра
      │ (основной)    │    │ (резервный)     │     идентичный конфиг,
      └───────┬───────┘    └────────┬────────┘     тот же secret
              │                     │
              └──────────┬──────────┘
                         │ ProxySQL 6033
                ┌────────▼─────────┐
                │    ProxySQL      │  ← отказ 2 (нужен парный)
                └────────┬─────────┘
                         │
                ┌────────▼─────────┐
                │  MySQL bg-core   │  ← отказ 3 (нужен парный)
                └──────────────────┘
```

### 4.3. Логика переключения по шагам

```
[1] BRAS шлёт Access-Request на primary
[2] Ответ получен            → работаем дальше, таймер сброса
[3] Ответа нет               → повтор (retries, обычно 3)
[4] Повторы исчерпаны        → пометить primary DEAD
[5] Отправка на secondary    → абонент авторизуется, сессия живёт
[6] Каждые dead-time         → пробный запрос на primary
[7] Primary ответил          → перевести на него новых абонентов
```

### 4.4. Где смыкаются лиза и переключение — ключевая формула

Задача ставит два числа в зависимость, и это правильно. Связка:

```
время переключения  ≈  radius-timeout × retries  +  dead-time
лиза абонента       ≥  время переключения        ← иначе сессия умрёт ДО переключения
```

Типовые значения: `radius-timeout = 3s`, `retries = 3` → ~9 с до пометки мёртвым + `dead-time` (обычно 30–60 с). Итого порядка 40–70 секунд.

**Вывод для задачи:** лиза 1 час при таком переключении — с большим запасом покрывает failover. Реально лизу можно ставить существенно короче, ограничение — не нагрузка на RADIUS при учащённых запросах. Значит:

- **Минимум, который просит Радик (лиза ≥ время переключения)** — выполняется при лизе в 5–10 минут.
- **Его целевой 1 час** — выполняется с запасом в ~50–60 раз.
- Значит ограничение здесь **не в failover, а в частоте запросов** → нужен расчёт нагрузки на `BGInetAccess` при учащённой лизе.
