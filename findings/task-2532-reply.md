# Ответ для сетевиков — задача 2532

Черновик сообщения в задачу. Адресовано сетевому отделу.

Коллеги, по задаче — нужна ваша часть. Разбор ниже.

## Что входит в вашу часть

Из формулировки задачи два пункта, и оба настраиваются **на BRAS, а не на RADIUS-сервере**:

1. **Сокращение DHCP-лизы** у абонентов РТ, РТЦ, ЮТК Ростов — параметр живёт на BRAS/DHCP-сервере.
2. **Автопереключение на резервный RADIUS** — настраивается в конфиге BRAS (radius-server group, dead-time, dead-criteria).

Подготовка самого второго экземпляра RADIUS — отдельная часть, её ведёт эксплуатация платформы BGBilling. Ваша — BRAS.

## Что нужно от вас

**Данные для расчёта:**

- модель и конфиг BRAS по площадкам РТ, РТЦ, ЮТК Ростов;
- **отдельно по Ростову** — в аудите доступов этого узла нет вообще, его нужно описать;
- текущее значение лизы у абонентов;
- **тип доступа: PPPoE или IPoE** — это критично. При PPPoE лизы как таковой нет, сессию держит `Session-Timeout`, который отдаёт RADIUS, и правка уйдёт в другое место. При IPoE/DHCP лиза на DHCP-сервере;
- текущие параметры `radius-timeout`, `retries`, `dead-time` (или аналоги на вашей модели);
- число абонентов на площадке — нужно, чтобы оценить нагрузку на RADIUS при учащённых запросах.

**Настроить после подготовки второго RADIUS:**

- secondary-сервер в radius-server group;
- `dead-time` и критерии пометки сервера мёртвым;
- идентичный shared-secret (его предоставит эксплуатация платформы).

## Логика переключения

```
ABONENT → BRAS → primary RADIUS
                      │
          нет ответа × retries (обычно 3×3с)
                      │
          сервер помечен DEAD
                      │
          запрос уходит на secondary  → сессия живёт
                      │
          каждые dead-time — пробный запрос на primary
                      │
          primary ответил → новых абонентов на него
```

## Ключевая формула — лиза и переключение

Задача ставит два числа в зависимость, и это правильно:

```
время переключения ≈ radius-timeout × retries + dead-time
лиза абонента      ≥ время переключения     ← иначе сессия умрёт ДО переключения
```

При типовых значениях (3с × 3 попытки + dead-time 30–60с) получается порядка **40–70 секунд**.

**Что из этого следует:**

- Целевая лиза в 1 час покрывает переключение с запасом ~50 раз.
- Реально лизу можно ставить заметно короче — ограничение тут **не в failover, а в нагрузке** на `BGInetAccess` при учащённых запросах. Поэтому и нужен расчёт по числу абонентов.
- Минимально допустимая лиза — больше времени переключения. Если поставите, например, 5 минут, это тоже закроет требование.

## Что важно про цепочку

RADIUS-серверы в этой платформе — **не FreeRADIUS**, а Java-приложения BGBilling Inet, и **локальной СУБД на них нет**: авторизация идёт по сети в MySQL через ProxySQL.

Значит, если на BRAS будет настроено только переключение между двумя RADIUS, а упадёт ProxySQL или БД на ядре — абоненты встанут всё равно, переключение не спасёт. Учитывайте это при проектировании и при тестировании: проверять падение нужно по всей цепочке, а не только RADIUS-хоста.

## Что уже сделано и что готовит вторая сторона

- Подготовка второго экземпляра `BGInetAccess`/`BGInetAccounting` с идентичным secret — ведёт эксплуатация платформы.
- Перед этим там же закроют: порт `1951/tcp` (управляющая консоль без аутентификации, открыта наружу), ограничат `1812/1813/2001 UDP` до NAS/BRAS, разберутся с Java от root и Debian 11 EOL.

## Когда будет готово с нашей стороны

Как только получим модель/конфиг BRAS и подтверждение по типу доступа — посчитаем фактическое время переключения и предложим значение лизы под вашу площадку.

По Ростову отдельно: если оборудование там своё и в аудите его не было — опишите, что стоит, иначе параметры под них считать не на чем.
